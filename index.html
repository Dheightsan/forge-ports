Inside my own pack

Other people's mods, in my own world, made to work together. Nobody pays me for this one: it is where I find out what breaks before a client does.

Fresh Animations on the mobs, Epic Fight on the player

Everything was configured correctly and Epic Fight kept winning anyway. The datapack was never loading: a missing pack.mcmeta, and not one line in the log.

Reading the split

Fresh Animations on almost every creature, Epic Fight on my character alone. Taking a mob off Epic Fight needs two changes, not one: a datapack entry stops its combat patch, but the mob still draws through its own renderer, so Fresh Animations never gets a look in. The other half is a script that pulls the mob out of that renderer map on world load. I found the split by decompiling the render engine, not by guessing.

The half that hid the longest. The datapack was not loading at all. It was missing its pack.mcmeta, so the loader skipped the entire folder and said nothing about it in the log. Both halves now name the same 24 mobs, and they still match today.

Fresh Animations is by FreshLX, Epic Fight by its own team. All I did was make them share a world.

I measured which mods animate themselves instead of assuming

48% of their creatures were already animated and never needed Fresh Animations at all. I scanned the bytecode of 645 jars instead of guessing.

The numbers

Fresh Animations does nothing for a mod that animates its own creatures, so before touching anything I scanned the bytecode of 645 jars for GeckoLib, AzureLib and Citadel. 305 add creatures, 3,951 creatures between them, and 48% of those creatures were already animated. That is the difference between a job with no edges and a short list.

One missing letter that silenced the spawns of seven mods

Seven mods loaded perfectly and their creatures never appeared anywhere. Their folder was biome_modifier. Forge reads biome_modifiers.

Why nothing warned me

Forge reads biome modifiers from a folder called biome_modifiers. A folder called biome_modifier is ignored: no warning, no error, nothing in the log. Seven mods in my pack had the singular, so they loaded perfectly and their creatures simply never appeared anywhere in the world. It looks exactly like a mod that is broken, and it is a plural.

A mod that was written off as unfixable, and the one word that fixed it

Written off as needing its bytecode rewritten. The fix was one word, and the pack went from 588 mods loading to 589 of 589.

The one word

Mutant More had been sitting out of my pack for weeks, crashing on load. The previous read was that its bytecode would have to be rewritten. It did not. Its mixin config declared compatibilityLevel: "JAVA_16" while all 577 of its classes were compiled as Java 17, so the mixin loader refused every one of them. Java 16 caps at class version 60; the classes were 61.

The fix was one word. JAVA_16 became JAVA_17. Before touching it I opened mixin-0.8.5.jar, the version Forge 1.20.1 loads, and read its CompatibilityLevel enum to confirm JAVA_17 was a value it would actually accept rather than assuming. Original jar backed up first, repacked, and the pack went from 588 mods loading to 589 of 589.

Mutant More is by AlexandersFunAndGames. That config line was the only thing I touched, and only in my own copy.

The long version, for whoever wants it. Five failures of my own that pass every automatic gate: the build succeeds, the log stays clean, and the mod is still wrong.

A crash the compiler cannot see

Read the detail

In my port of Capybara (39Choko, MIT) the model asked for a bone called saddleParts. In the model file that bone is called saddle. The name lives inside a text string, so nothing checked it. The build passed. The resource diff passed. It crashed the first time a capybara was drawn, in my own test instance. GeckoLib's AnimationProcessor.getBone returns null for a name the model does not have, and the renderer runs every frame.

Proof. I kept the broken jar. The check now reads bone names straight out of the compiled bytecode with javap and compares them against the model file. On the fixed jar: one bone found, zero failures. On the broken jar: it fails, names saddleParts, and prints the 11 bones that do exist. I wrote up how to run that check on your own jar.

Files that vanish in the repack

Read the detail

A port is a rebuild, not a copy. Recipes, loot tables and textures can go missing when the jar is repackaged, and nothing errors. The mod loads and quietly does less than it did before.

Proof. I diff every asset, data and licence file against the jar the original author published. Across Boids and Birds (Tomate0613, MIT) and Capybara (39Choko, MIT): 22 of the 28 are byte identical. 6 are JSON the build reformatted, and they parse to exactly the same data. Two files are added, both Forge biome modifiers so spawns work on this loader. Loader metadata is replaced on purpose, mods.toml where Fabric had fabric.mod.json. Unzip both jars and run the same diff.

Yarn names and Mojang names do not line up

Read the detail

Fabric source is written in Yarn names. Forge builds against Mojang's. I bridge them in two hops through intermediary mappings, and the translator only rewrites a name when it has exactly one possible target. Anything ambiguous is left for the compiler to reject.

Proof. It still gets things wrong, and those mistakes compile. On Capybara the jungle spawn biome came out of the translator as JUNGLE_PLANKS. That is why I read translated output back against the original source before it goes into a build. The jungle, mangrove swamp and sparse jungle spawns in that port came from the original, not from the translated text.

Fine in singleplayer, dead on the server

Read the detail

A clientbound packet handler written as a method reference is resolved where it is registered. A dedicated server has no client class to resolve, so registration can take the server down at startup while singleplayer never complains.

Proof. On a network layer backport from 1.21 to Forge 1.20.1, on my own modpack, I rebuilt every packet payload by hand: 22 serverbound, 19 clientbound. All 19 clientbound handlers are explicit lambdas with the client call behind a Dist.CLIENT guard, and all 41 register from one shared method with sequential IDs, so the two sides cannot drift. That is how the code is written, not a test result. I do not name the mod here: it is a personal-use port and I have no written permission from the author to put its name on a commercial page.

Mixins that quietly do not load

Read the detail

Repackaging a jar can drop the manifest entry that declares its mixin configs. Forge then loads the mod without complaint and none of the mixins apply. The mod is installed, part of its behaviour is missing, and nothing in the log says so.

Proof. Same class of bug, same answer: it became a check. The manifest one in the five checks I run is this exact bug, turned into something a script can catch. They are a colander, not a proof. The bone check only sees literal names, and it needs a JDK to read the bytecode.
