It compiles. That proves nothing.

None of this is client work. It is my own porting. These are five failures that pass every automatic gate: the build succeeds, the log stays clean, and the mod is still wrong. For each one, what actually causes it, and what now runs before a jar leaves my machine.

A crash the compiler cannot see

In my own port of Capybara (39Choko, MIT) the model asked for a bone called saddleParts. In the model file that bone is called saddle. The name lives inside a text string, so nothing checked it. The build passed. The resource diff passed. It crashed the first time a capybara was drawn, in my own test instance. GeckoLib's AnimationProcessor.getBone returns null for a name the model does not have, and the renderer runs every frame.

Proof. I kept the broken jar. The check now reads bone names straight out of the compiled bytecode with javap and compares them against the model file. On the fixed jar: one bone found, zero failures. On the broken jar: it fails, names saddleParts, and prints the 11 bones that do exist.

Files that vanish in the repack

A port is a rebuild, not a copy. Recipes, loot tables and textures can go missing when the jar is repackaged, and nothing errors. The mod loads and quietly does less than it did before.

Proof. Every asset, data and licence file is diffed against the jar the original author published. Across Boids and Birds (Tomate0613, MIT) and Capybara (39Choko, MIT): 28 files, none missing. 22 are byte identical. 6 are JSON the build reformatted, and they parse to exactly the same data. Two files are added, both Forge biome modifiers so spawns work on this loader. Loader metadata is replaced on purpose, mods.toml where Fabric had fabric.mod.json. Unzip both jars and run the same diff.

Yarn names and Mojang names do not line up

Fabric source is written in Yarn names. Forge builds against Mojang's. I bridge them in two hops through intermediary mappings, and the translator only rewrites a name when it has exactly one possible target. Anything ambiguous is left for the compiler to reject.

Proof. It still gets things wrong, and those mistakes compile. On Capybara the jungle spawn biome came out of the translator as JUNGLE_PLANKS. That is why translated output is read back against the original source before it goes into a build. The jungle, mangrove swamp and sparse jungle spawns in that port came from the original, not from the translated text.

Fine in singleplayer, dead on the server

A clientbound packet handler written as a method reference is resolved where it is registered. A dedicated server has no client class to resolve, so registration can take the server down at startup while singleplayer never complains. Nobody testing solo will ever see it.

Proof. On a network layer backport from 1.21 to Forge 1.20.1, on my own modpack, I rebuilt 41 packet payloads: 22 serverbound, 19 clientbound. All 19 clientbound handlers are explicit lambdas with the client call behind a Dist.CLIENT guard, and all 41 register from one shared method with sequential IDs, so the two sides cannot drift. That is how the code is written, not a test result. I do not name the mod here: it is a personal-use port and I have no written permission from the author to put its name on a commercial page.

Mixins that quietly do not load

Repackaging a jar can drop the manifest entry that declares its mixin configs. Forge then loads the mod without complaint and none of the mixins apply. The mod is installed, part of its behaviour is missing, and nothing in the log says so.

Proof. Same class of bug, same answer: it became a check. Five structural checks now run against every jar I build, before anything is launched: mod metadata, pack format, bytecode version, mixin declarations in the manifest, and model bones. They are a colander, not a proof. The bone check only sees literal names, and it needs a JDK to read the bytecode.

Most devs in this space ignore licensing. I don't, because a DMCA takedown or account ban hits your account harder than it hits me.

Public: open-source & compatibility

Open-source mods (MIT · Apache · LGPL), mods with written permission, and compatibility add-ons (my own code, depending on mods you install yourself) get published to CurseForge & Modrinth, with full credit to the original authors.

Private: closed-source mods

Most requested mods are closed-source. You bring one you have the right to use; I modify it for you and deliver privately, to you only, never published. You pay for my time, not for redistribution.

What I won't do

Publicly redistribute a closed-source (All Rights Reserved) mod without written permission from the author. I don't bend on this. It's what keeps your accounts safe from takedowns and bans.

The principle: you're paying for my time writing the work, not for the right to distribute it. The right to publish stays with whoever holds the licence. As far as I can tell, that's the only way to run a porting service that won't get someone banned.
